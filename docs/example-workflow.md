# Example Workflow

This is a synthetic explanatory workflow. It does not replace the frozen Public Core v1 Quickstart or any canonical OASYS protocol.

The scenario uses only Public, synthetic state. It contains no Greywolf-private operational history and creates no OASYS authority.

Its purpose is simple:

show what using OASYS can look like when documented state crosses a session boundary, a required decision is missing, and execution must stop until the Operator supplies that authority.

## Stage 1 — Documented Starting State

A synthetic work unit already exists.

The previous action is complete, the current work area is known, and the scope is bounded.

One decision remains unresolved.

| State | Documented value |
| :----- | :----- |
| Previous action | Completed |
| Current work area | Synthetic Work Unit A |
| Scope | Continue only within Work Unit A |
| Required decision | Select Option A or Option B |
| Operator selection | Unresolved |
| Next action | Continue only after an explicit branch selection |

The Operator has not selected Option A or Option B.

The unresolved decision is part of the documented state. It is not permission for the Architect to choose.

For this explanatory workflow, these facts are contained in a synthetic Public documented execution-state artifact supplied for this scenario. That scenario-specific state is not a fifth mandatory Reconstruction-base artifact and creates no authority outside this example.

## Stage 2 — Fresh Execution Context

The work continues in a new session.

The new session may have no reliable conversational continuity with the earlier one.

OASYS does not treat remembered conversation, familiarity with the project, or an apparently obvious next step as authoritative state.

It also does not give the LLM literal persistent memory.

The continuation must instead be established from the supplied authoritative documents and documented state.

## Stage 3 — Reconstruction

The fresh context reconstructs Public Core v1 using the exact mandatory Reconstruction base:

1. Bootstrap v2.5.0
2. OASYS — Master Index aligned to Bootstrap v2.5.0
3. C-Log 2026-08-24_001
4. OASYS — Cross-Session Reconstruction Protocol v2.0

These four artifacts establish the mandatory Public Core Reconstruction base.

Because this example also continues a specific documented work state, the synthetic execution-state artifact from Stage 1 is supplied as applicable scenario-specific documented state. It remains Conditional / Operation-Specific material rather than becoming a fifth mandatory Reconstruction artifact.

Three boundaries remain explicit:

- this is Reconstruction, not Initialization;
- fresh-session Reconstruction is not formal OASYS Rotation;
- package presence does not mean every Public Core runtime authority is loaded for this operation.

Reconstruction uses the authority required for Reconstruction.

Other artifacts remain separate unless applicable authority actually requires them.

## Stage 4 — Separate Synchronization

After Reconstruction, Synchronization begins as its own governed operation under:

**OASYS — Operator–Architect Sync Protocol v1.0**

For this synthetic example, Synchronization uses the reconstructed documented state together with the explicitly identified active checklist to align:

- previous action: completed;
- current work area: Work Unit A;
- scope: remain within Work Unit A;
- next explicit action: continue after an authorized branch selection;
- branch decision: unresolved;
- active checklist: explicitly identified for this synthetic synchronization event.

The active checklist and documented state are operation-specific inputs.

They do not become:

- another universal Public Core runtime authority;
- a fourth Initialization artifact;
- a fifth Reconstruction artifact.

Synchronization now has enough documented information to align the state of the work—but it still has no authority to choose the unresolved branch.

## Stage 5 — Missing-Authority Boundary

The workflow reaches the branch decision:

Option A or Option B?

No Operator selection exists.

Valid OASYS-governed execution must not resolve that missing authority by:

- choosing A because it looks more likely;
- choosing B because it appears more efficient;
- using “best judgment”;
- inferring a preference from conversation;
- treating pressure to continue as authorization.

The missing requirement is identified exactly:

**Explicit Operator branch selection required.**

### Non-Inference

The missing decision is not invented.

### Fail-Closed Execution

Only the affected continuation remains blocked.

The runtime may explain why it cannot proceed, but it must not represent either branch as authorized.

The documented state therefore remains:

**Branch selection: unresolved.**

## Stage 6 — Operator Resolution

The Operator explicitly selects:

**Option A**

That supplies the previously missing decision authority.

This does not bypass OASYS governance.

The Operator does not arbitrarily bypass governance.

The Operator is resolving a decision that the governing workflow explicitly required the Operator to make.

The rest of the documented boundaries remain unchanged:

- Work Unit A remains the scope;
- prior completed state remains completed;
- Option B remains unselected;
- no unrelated capability or continuation is authorized.

## Stage 7 — Governed Continuation

Synchronization can now align the operative state:

- Operator intent: continue through Option A;
- documented state: previous action completed;
- scope: Work Unit A only;
- selected branch: Option A;
- next authorized action: continue the documented Option A work;
- Option B: not authorized.

Valid OASYS-governed continuation proceeds only on the explicitly selected branch.

The example does not claim that every probabilistic model will always comply perfectly.

It illustrates the behavior required by the governed architecture:

unresolved authority is preserved until the required authority actually exists.

## Illustrated Result

Within this synthetic example, the workflow illustrates several OASYS mechanisms:

- State crossed the session boundary through documents, not assumed conversational memory.
- Reconstruction and Synchronization remained separate operations.
- Fresh-session Reconstruction was not treated as formal Rotation.
- Repository presence did not become a “load everything” rule.
- The unresolved branch was not inferred.
- Fail-closed behavior remained localized to the blocked continuation.
- The exact missing authority was identified.
- The Operator supplied the missing decision explicitly.
- Operator authority operated within governance rather than replacing it.
- Continuation remained inside the documented scope.
- No Greywolf-private history, hidden conversational state, or undisclosed Private dependency was required.

This makes the workflow's authority, state, block, resolution, and continuation understandable without requiring access to hidden model reasoning.
